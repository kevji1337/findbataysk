## 2. Аудит существующего бота

### 2.1 Границы текущей логики

```
main.py
  ├── start.router      → /start, back_to_menu, cancel_action
  ├── referral.router   → referral_program, on_chat_member_update, claim_referral_gift
  ├── advertising.router→ критерии, заявка, ad_approve/ad_reject
  ├── admin_contact.router
  └── admin.router      → /admin, admin_panel, admin_top_referrers, admin_requests:*
```

**Критические точки:**

- **Реферальная логика:** `bot/services/referral_events.py` — единственное место изменения `referral_count` и `ReferralEvent`. Используется `get_session()` и UPSERT по `telegram_id` (ON CONFLICT DO NOTHING), повторный вход не увеличивает счётчик.
- **БД:** SQLAlchemy async, одна точка входа — `bot/database/models.py`: `engine` + `async_session` из `settings.database_url`. Поддержка PostgreSQL и SQLite (диалект в `referral_events.py`).
- **FSM:** SQLite (`fsm_storage.db`) — отдельный файл, только для состояний (например, ввод ссылки на рекламу).
- **Секреты:** `bot/config.py` — Pydantic Settings из `.env`: `BOT_TOKEN`, `CHANNEL_ID`, `ADMIN_IDS`, `DATABASE_URL`, `AD_CRITERIA`.

### 2.2 Риски при доработках

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Поломка учёта рефералов при миграции БД | Средняя | Тесты `test_referral_events.py` + проверка консистентности после миграции |
| Рассылка вызовет баны | Высокая | Rate limit (например 25 msg/сек), задержки, retry с экспоненциальной задержкой, idempotency по user_id |
| Двойной учёт / гонки | Низкая | Уже покрыто: unique `telegram_id` в `ReferralEvent`, атомарный join в одной транзакции |
| Потеря FSM при переезде | Средняя | Перенос `fsm_storage.db` или переключение FSM на Redis/Postgres при необходимости |

## 3. Архитектура: до / после

### 3.1 Сейчас (до)

```
[ Telegram ]
      │
      ▼
[ Bot process ]  ← aiogram polling
      │
      ├── DATABASE_URL ──► [ Postgres или SQLite ]  (users, referral_*, advertising_requests)
      │
      └── SQLite file ──► fsm_storage.db (FSM)
```

- Один процесс бота.
- БД: одна (Postgres или SQLite по `DATABASE_URL`).
- FSM: отдельный SQLite-файл в текущей директории.

### 3.2 После (целевая)

```
[ Telegram ]
      │
      ▼
[ Bot container ]  ← тот же код, те же роутеры
      │
      ├── DATABASE_URL ──► [ Supabase Postgres ]  (внутри Docker-сети)
      │
      ├── (опционально) FSM в Redis или в Postgres — для консистентности бэкапов
      │
      └── [ Supabase stack ]
            ├── Postgres (данные бота)
            ├── Auth (если позже понадобится для веб-админки)
            └── Storage (если появятся медиа-файлы рассылок)
```

- Бот остаётся единственной точкой входа для Telegram; Supabase — только БД (и при необходимости Auth/Storage).
- Текущие пользователи и бизнес-логика сохраняются за счёт того, что меняется только `DATABASE_URL` и окружение (Docker).

## 4. Docker + Supabase архитектура

### 4.1 Структура контейнеров

Рекомендуется **Docker Compose** (Kubernetes не обязателен для одного бота и одной БД).

```yaml
# docker-compose.yml (схема)
services:
  bot:
    build: .
    env_file: .env
    environment:
      DATABASE_URL: postgresql+asyncpg://postgres:${POSTGRES_PASSWORD}@db:5432/postgres
      # FSM можно оставить SQLite в volume или переключить на Redis
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: supabase/postgres:15.1.0.147  # или актуальный образ Supabase Postgres
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./supabase/migrations:/docker-entrypoint-initdb.d  # опционально, начальные скрипты
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5

  # Опционально: Redis для FSM (чтобы не терять состояния при рестарте и для мультиинстанса)
  # redis:
  #   image: redis:7-alpine
  #   restart: unless-stopped

volumes:
  postgres_data:
```

- **Self-hosted Supabase:** можно поднять полный стек (Kong, Auth, Postgres, Realtime, Storage, etc.) по [официальной инструкции](https://supabase.com/docs/guides/self-hosting) или минимально — только **Postgres** с тем же форматом данных. Для бота достаточно Postgres; Auth/Storage подключаются при появлении веб-части или файлового хранилища.
- Секреты: `POSTGRES_PASSWORD`, `BOT_TOKEN` и т.д. — из `.env`, не в коде. В продакшене — secrets в Docker/CI или внешнее хранилище (Vault, облачные secrets).

### 4.2 Переменные окружения (env)

```bash
# Обязательные
BOT_TOKEN=your_bot_token_from_botfather
CHANNEL_ID=-100xxxxxxxxxx
ADMIN_IDS=123456789
DATABASE_URL=

# Опционально (feature flags)
BROADCAST_ENABLED=true
LEADERBOARD_ENABLED=true

# Рассылка (лимиты)
BROADCAST_DELAY_SEC=0.05
BROADCAST_BATCH_SIZE=25
```

Резервное копирование: регулярный `pg_dump` контейнера `db` в объектное хранилище (S3-совместимое или хост).

## 5. План миграции данных

### 5.1 Стратегия (zero / near-zero downtime)

1. **Подготовка нового хоста**
   - Развернуть Docker Compose с Postgres (Supabase Postgres или обычный Postgres 15).
   - Применить миграции Alembic на новую БД (`alembic upgrade head`).

2. **Перенос данных**
   - Остановить запись в старую БД не обязательно: использовать **однонаправленную синхронизацию**:
     - Запустить однократный скрипт миграции (dump/restore или `INSERT ... SELECT` через временный канал), пока бот ещё на старой БД.
     - Или: остановить бота, сделать `pg_dump` (или экспорт SQLite → SQL), загрузить в новую Postgres, проверить целостность, переключить бота на новую БД и запустить.
   - Рекомендуемый вариант при возможности короткого даунтайма: **остановка бота → pg_dump старой БД → restore в новую → переключение `DATABASE_URL` → запуск бота**. Даунтайм 2–5 минут.

3. **Порядок переключения трафика**
   - Обновить на новом хосте только `DATABASE_URL` (и при необходимости FSM).
   - Перезапустить контейнер бота.
   - Трафик Telegram не переключается (тот же бот, тот же токен); переключается только сервер, где крутится контейнер.

4. **Работа с секретами**
   - На новом хосте свой `.env` с новым `DATABASE_URL`.
   - Остальные секреты (BOT_TOKEN, ADMIN_IDS) — те же.

5. **Резервное копирование**
   - До миграции: полный бэкап старой БД и `fsm_storage.db`.
   - После миграции: регулярный cron внутри хоста или CI: `docker exec db pg_dump -U postgres ... > backup_$(date +%Y%m%d).sql` и выгрузка в хранилище.

6. **Валидация после миграции**
   - Сравнить количество записей: `users`, `referral_links`, `referrals`, `referral_events`, `advertising_requests`.
   - Запустить тесты: `pytest tests/test_referral_events.py` против новой БД.
   - Ручная проверка: один админ заходит в бота, проверяет реферальную ссылку, админ-панель, топ рефереров.

### 5.2 Скрипт миграции (псевдокод)

```python
# scripts/migrate_to_new_db.py (концепт)
# 1. Подключиться к старой БД (из env OLD_DATABASE_URL)
# 2. Подключиться к новой БД (из env DATABASE_URL)
# 3. Отключить FK при импорте (если нужно), порядок: users → referral_links → referrals → referral_events → advertising_requests
# 4. SELECT из старой → INSERT в новую (batch по 1000), сохраняя id где нужно (или сбросить sequence после)
# 5. Включить FK, обновить sequences для Postgres
# 6. Вывести отчёт: количество строк по таблицам
```

Для полного даунтайм-переноса проще: `pg_dump old_db | psql new_db` (при совместимости версий Postgres) или экспорт SQLite в CSV и загрузка в Postgres скриптом.

## 6. Модель данных

### 6.1 Текущая (уже есть в коде)

- **users** — id, telegram_id (unique), username, first_name, created_at.
- **referral_links** — id, user_id (FK users), invite_link (unique), referral_count, gifts_claimed, created_at.
- **referrals** — id, referral_link_id, telegram_id, joined_at (история переходов; счётчик живых хранится в referral_events + referral_count).
- **referral_events** — id, referral_link_id, telegram_id (unique), first_join_at, last_join_at, left_at, status (joined/left), is_counted — основа для корректного учёта и вычитания при выходе.
- **advertising_requests** — id, user_id, channel_link, status, created_at, reviewed_at.

### 6.2 Расширения под ТЗ

- **Лидерборд по периодам (доступен всем пользователям)**  
  Кнопка в главном меню «Топ по приглашениям» для всех пользователей (не только админов). Текущая схема позволяет считать «топ за период» по `referral_events`: считаем только события с `first_join_at` в диапазоне и `is_counted = true` на момент учёта, или сумму прироста за период по ссылкам. Рекомендация: не менять схему, добавить представление или запрос в `ReferralStatsRepository`: например `get_top_referrers(limit, since_date=None)` с фильтром по `ReferralEvent.first_join_at` и учётом вычетов (реферал вышел — не считаем в периоде). Для «всё время» — как сейчас по `ReferralLink.referral_count`.

- **Уведомления вкл/выкл**  
  В таблицу **users** добавить колонку `referral_notifications_enabled BOOLEAN DEFAULT true`. Перед вызовом `notify_user_new_referral()` проверять этот флаг. Миграция Alembic: одна колонка.

- **Рассылка**  
  Отдельная таблица не обязательна для MVP: рассылка «всем пользователям» = выборка `User.telegram_id` и последовательная отправка. Для истории рассылок (опционально): таблица `broadcast_jobs` (id, created_at, created_by_admin_id, message_type, text, media_file_id, status, sent_count, failed_count).

## 7. Антифрод и edge-кейсы

### 7.1 Реферальная система (уже учтено в коде)

- **Один пользователь = один учёт:** уникальный `telegram_id` в `ReferralEvent`, при повторном входе по той же ссылке — `ON CONFLICT DO NOTHING`, счётчик не увеличивается.
- **Выход = вычитание:** при `left` обновляется `is_counted=False` и `referral_count` уменьшается на 1 (с проверкой `referral_count > 0`).
- **Race join:** два одновременных `handle_referral_join` для одного telegram_id — только один INSERT из-за unique; тест `test_referral_join_race_condition` это проверяет.
- **Race leave:** два одновременных `handle_referral_leave` — оба прочитают один и тот же event, оба могут сделать decrement; в коде один раз ставится `status=left`, второй раз `decremented=False`. Нужно убедиться, что decrement идёт только один раз (сейчас логика: при первом leave — decrement, при втором — только обновление статуса уже left, без второго decrement). По текущей реализации второй вызов вернёт `decremented=False` и не уменьшит счётчик повторно — ок.

### 7.2 Защита от накрутки лидерборда

- Учитывать только «живых» рефералов (is_counted) или явно считать по событиям за период, без дублей.
- Ограничение: один telegram_id = максимум один вклад в счёт по одной ссылке (уже гарантировано схемой).
- При необходимости: порог минимального времени в канале (например не считать реферала, вышедшего за &lt; 1 минуты) — тогда в `handle_referral_leave` можно не вычитать, если `joined_at` было недавно; это опционально и может быть вынесено в конфиг.

### 7.3 Рассылка

- **Rate limits Telegram:** ~30 msg/сек к разным чатам; использовать задержку между сообщениями (например 0.05–0.1 сек) и батчи.
- **Бан/блокировка:** часть пользователей могла заблокировать бота — при `TelegramForbiddenError` (или аналог в aiogram) помечать в лог и не повторять бесконечно; retry только по временным ошибкам (сетевые, 429).
- **Idempotency:** рассылка «всем» без сохранения состояния — повторный запуск отправит снова. Для идемпотентности хранить в `broadcast_jobs` последний отправленный telegram_id или множество отправленных и при перезапуске досылать только не охваченным.

## 9. Масштабирование

- **Текущий масштаб:** один инстанс бота достаточно для десятков тысяч пользователей при polling.
- **Рост нагрузки:** при очень высокой частоте обновлений можно перейти на webhook (один инстанс или балансировка по пути), увеличить количество воркеров только при использовании очередей (например, рассылка в фоне через Celery/RQ).
- **БД:** Postgres (Supabase) выдержит рост таблиц; при необходимости — индексы по `(referral_events.referral_link_id, first_join_at)` для лидерборда за период, по `users.telegram_id` уже есть.
- **Рассылка:** выполнять в фоне (asyncio task или отдельный воркер), не блокируя обработку сообщений; батчами с паузой.

## 10. Риски и rollback-стратегия

| Риск | Вероятность | Действие при сбое |
|------|-------------|-------------------|
| Миграция БД: потеря/расхождение данных | Низкая | Хранить полный бэкап старой БД; при проблемах — вернуть старый хост и старый `DATABASE_URL`, откатить деплой бота |
| Поломка реферальной логики после деплоя | Низкая | Прогон `pytest tests/test_referral_events.py` на новой БД до переключения; при баге — откат к предыдущему образу контейнера и старой БД |
| Рассылка ломает бота или даёт бан | Средняя | Feature flag `BROADCAST_ENABLED=false` отключает кнопку и обработчики рассылки без деплоя; при бане — пауза рассылки, разбор логов |
| Новый хостинг недоступен | Средняя | Держать старый сервер и старую БД до подтверждения стабильности; переключение DNS/запуск бота обратно на старый хост при инциденте |
| Supabase Postgres не поднимается | Низкая | Healthcheck в compose; ручной запуск миграций и проверка подключения до переключения бота |

**Rollback по шагам:**

1. Остановить контейнер бота на новом хосте.
2. На старом хосте (или резервном) выставить `DATABASE_URL` на старую БД, запустить старую версию бота.
3. Убедиться, что пользователи и реферальные счётчики отображаются корректно.
4. Разбор причин и повтор миграции после исправлений (бэкапы не трогать до завершения расследования).
